# CrewAssist behaviour tests

A small jsdom suite that boots the **real `index.html`** in a fake browser and drives it the way a person would: tapping buttons, typing into fields, answering dialogs, faking flight fetches. No build step, no browser, no network. Runs in ~25 seconds.

## Run it

```bash
cd tests
npm install        # once; installs the pinned jsdom (see package.json)
npm test           # or: node run-all.js
```

`node_modules/` and the lockfile are git-ignored (repo convention) — the pinned version lives in `tests/package.json`. If jsdom ever needs bumping, bump it deliberately and re-run everything.

## Conventions (what keeps this evergreen)

1. **Assert outcomes, not internals.** "The share panel received the file", not "function X called function Y". Outcome tests survive refactors — the export logic was rewritten twice without touching these assertions.
2. **New features bring their test block.** The feature's "verify" step becomes a permanent suite block, added in the same sitting as the feature.
3. **Intentional behaviour changes update the matching block.** A failing test after a deliberate spec change is the net doing its job — re-sign the contract in the same commit. The cost stays proportional: minutes, never a rewrite.
4. **IDs are contracts.** The app's element ids (`btn-dev-save`, `ca-arch-trash`, …) are stable and pinned by the owner's specs; tests may rely on them. classNames only where the spec pins them (colours, pill styling).
5. **Date-anchored seeds.** Suites that depend on "today" (current-month expansion, partial-month projections, month badges) seed the real current calendar month and **compute date-derived expectations from the run date** — never hardcode the day. A calendar rollover fails them loudly on purpose: reseed the months and figures, never change app behaviour to match stale seeds. Two traps hotfix 9 added to this rule: seeds compared against a ROLLING window (the backup nudge's "newer than the last export") must derive from the run date, not fixed ones — a fixed date crosses the window overnight; and seeds built from bare `hh:mm` strings must carry the true `ymd`/`staYmd` of real moments — near midnight the strings straddle the day boundary and trip the app's overnight-arrival rule (a 02:17 SGT run caught both). The harness pins the box to Asia/Singapore (`process.env.TZ` at require time) because the app's naive wall math (expiry sweeps, day labels) and its zone-aware station math agree only on the crew's own clock — an unpinned box can split them (the 2026-10-03 UTC sandbox did, and exposed a real on-device date bug); the pin is why.
6. **Timing:** the harness boots jsdom and waits 400ms — jsdom fires its own `DOMContentLoaded` exactly once. **Never dispatch it manually**; double-firing double-binds every listener (a real bug this suite caught). Dialog close fades take 200ms — wait ≥400ms after OK/Cancel before asserting `hidden`.

7. **`w.eval` sees function declarations, not `let` bindings.** Top-level `let`/`const` in the app's scripts never become window properties — assert through functions (`rcTintKind(...)`, `rosterCalSelect(...)`) or the DOM, never by eval-ing a variable name (hotfix 10's first heal pin died on `rcTL is not defined`).
8. **A sabotage must be able to evict the row.** The virtualized window renders ±6 rows of context, so scrolling a today near the timeline's start to the TOP cannot push its row out of the DOM — fling to the far bottom instead (hotfix 10).
